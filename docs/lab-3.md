# Лаба 3. Логика в базе

База сама следит за правилом своей темы и выполняет бизнес-операции одной командой. Частые запросы сохранены как представления, расчёты оформлены функциями, правило темы проверяет триггер, время изменения записи ставит служебный триггер. Всё создаётся скриптами из `db/` и показывается сценарием `demo/lab3.sql`.

## Теория

**Где хранить логику.** Правило, записанное в базе, работает для всех: для сайта, для скрипта, для человека в `psql`. Правило в коде приложения легко обойти, если писать в базу напрямую. В базу выносят то, что касается целостности данных: «на сеанс нельзя продать больше мест, чем в зале». Отправку писем и работу с внешними сервисами оставляют приложению.

**Представление (VIEW)** это сохранённый запрос с именем. Данных оно не хранит: при каждом обращении запрос выполняется заново, поэтому результат всегда актуальный. С представлением работают как с таблицей: `SELECT`, `WHERE`, `JOIN`.

```sql
CREATE VIEW v_session_card AS
SELECT s.id, f.title, h.name AS hall, s.starts_at
FROM sessions s JOIN films f ON f.id = s.film_id JOIN halls h ON h.id = s.hall_id;

SELECT * FROM v_session_card WHERE hall = 'Зал 1';
```

`CREATE OR REPLACE VIEW` меняет представление, новые колонки добавляются только в конец списка.

**Материализованное представление** хранит результат запроса как таблица. Читается быстро, но обновляется только командой `REFRESH MATERIALIZED VIEW`.

**Функция** принимает параметры и возвращает значение или таблицу. Вызывается внутри запроса: `SELECT free_seats(42);`. **Процедура** ничего не возвращает и вызывается командой `CALL`, внутри неё можно управлять транзакцией. Функции и процедуры пишутся на SQL (`LANGUAGE sql`, тело из одного запроса) или на PL/pgSQL (`LANGUAGE plpgsql`, есть переменные и условия).

```sql
CREATE FUNCTION free_seats(p_session integer)
RETURNS integer
LANGUAGE sql
AS $$
    SELECT h.seats - (SELECT count(*) FROM tickets t WHERE t.session_id = s.id)
    FROM sessions s JOIN halls h ON h.id = s.hall_id
    WHERE s.id = p_session;
$$;
```

Из чего состоит PL/pgSQL:

| Конструкция | Что делает |
| --- | --- |
| `DECLARE v_total integer;` | Объявляет переменную |
| `BEGIN ... END;` | Тело функции |
| `v_total := 5;` | Присваивание |
| `SELECT count(*) INTO v_total FROM ...;` | Результат запроса в переменную |
| `IF ... THEN ... ELSIF ... ELSE ... END IF;` | Условие |
| `RAISE EXCEPTION 'Мест нет: продано % из %', sold, total;` | Остановить операцию с ошибкой, вместо `%` подставляются значения |
| `RAISE NOTICE 'v_total = %', v_total;` | Напечатать сообщение, работа продолжается |
| `RETURN v_total;` | Вернуть результат |

**Бизнес-операция одной командой**: функция, которая выполняет действие целиком. Например, `buy_ticket(session_id, seat_id)` проверяет место, создаёт билет и возвращает его номер. Если на любом шаге возникла ошибка, отменяется всё, что функция успела сделать.

**Триггер** это функция, которую база вызывает сама при `INSERT`, `UPDATE` или `DELETE`. Триггер нельзя забыть вызвать, поэтому правило в нём соблюдается для любой команды.

| | `BEFORE` | `AFTER` |
| --- | --- | --- |
| Когда | До записи строки | После записи строки |
| Для чего | Проверить правило, поправить значения в `NEW`, отменить операцию ошибкой | Записать историю, обновить связанные данные |

Внутри триггера `NEW` содержит новую версию строки, `OLD` старую. У `INSERT` есть только `NEW`, у `DELETE` только `OLD`, у `UPDATE` обе. `BEFORE`-триггер возвращает `NEW`: строка записывается. `RETURN NULL` в `BEFORE`-триггере молча отменяет запись строки, без ошибки. `RAISE EXCEPTION` прерывает операцию с ошибкой, и изменения откатываются.

Триггер нужен там, где правило смотрит в другие строки или таблицы. Правило про одну строку проще и надёжнее записать через `CHECK`, `UNIQUE` или `NOT NULL`.

```sql
CREATE FUNCTION check_seats() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF (SELECT count(*) FROM tickets WHERE session_id = NEW.session_id)
       >= (SELECT h.seats FROM sessions s JOIN halls h ON h.id = s.hall_id WHERE s.id = NEW.session_id) THEN
        RAISE EXCEPTION 'На сеанс % больше нет мест', NEW.session_id;
    END IF;
    RETURN NEW;
END $$;

CREATE TRIGGER trg_check_seats BEFORE INSERT ON tickets
FOR EACH ROW EXECUTE FUNCTION check_seats();
```

**Служебный триггер** заполняет `updated_at` (время последнего изменения строки) или записывает в таблицу истории, кто, что и когда изменил. Колонка `updated_at` добавляется в новом скрипте: `ALTER TABLE orders ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now();`.

```sql
CREATE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END $$;

CREATE TRIGGER trg_orders_updated_at BEFORE UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

**Риски триггеров.** Логика скрыта: глядя на `INSERT`, не видно, что сработает ещё. Триггер выполняется для каждой строки и замедляет массовые операции. Триггер, который меняет свою же таблицу, может вызвать сам себя.

## Что сделать

Новые скрипты в `db/`: `10_views.sql`, `11_functions.sql`, `12_triggers.sql`. Скрипты лаб 1 и 2 не меняются, новая лаба добавляет слой поверх. Порядок важен: функция триггера создаётся раньше самого триггера.

Бизнес-правило берётся из своей темы в [themes.md](themes.md). В лабе 4 его нужно будет защитить от одновременных операций.

Сценарий `demo/lab3.sql` в формате [сценария](scenarios.md) показывает по шагам:

1. выборку из каждого представления;
2. вызов функции;
3. бизнес-операцию и результат в таблице;
4. нарушение правила: шаг с `-- expect: error "текст"`, база отвечает ошибкой триггера;
5. работу служебного триггера: изменили строку, `updated_at` обновился или в истории появилась запись.

```sql
-- 6. Последнее место на сеанс уже продано: ошибка триггера
-- expect: error "нет мест"
SELECT buy_ticket(1, 42);
```

## Чек-лист (6 баллов)

1. Два представления для частых запросов, оба читаются без ошибки. Например, карточка заказа с `JOIN` по нескольким таблицам
2. Функция возвращает значение или таблицу: стоимость заказа, свободные места
3. Бизнес-операция: функция или процедура меняет данные (`INSERT`, `UPDATE` или `DELETE`) и вызывается в `demo/lab3.sql`
4. Триггер правила темы с `RAISE EXCEPTION`. В `demo/lab3.sql` есть шаг, где правило нарушается, и база отвечает понятной ошибкой
5. Служебный триггер заполняет `updated_at` или пишет в таблицу истории
6. Все представления, функции и триггеры создаются скриптами из `db/`, все шаги `demo/lab3.sql` проходят

## ★ (2 балла): отчёт и поиск

- Материализованное представление с отчётом (например, выручка по месяцам) и его обновление `REFRESH MATERIALIZED VIEW` в `demo/lab3.sql`.
- Функция поиска с параметрами-фильтрами, которая возвращает таблицу (`RETURNS TABLE (...)`), как форма фильтров на сайте. Любой фильтр можно не передавать: `WHERE (p_city IS NULL OR city = p_city)`.

## ★★ (2 балла): журнал изменений

- Таблица-журнал для главной таблицы: операция, старое и новое значение в `jsonb` (`to_jsonb(OLD)`, `to_jsonb(NEW)`), кто (`session_user`) и когда (`clock_timestamp()`). Заполняется `AFTER`-триггером на `INSERT`, `UPDATE` и `DELETE`.
- Функция «состояние записи на дату»: принимает id и момент времени, возвращает `jsonb` с тем, какой была запись в этот момент.
