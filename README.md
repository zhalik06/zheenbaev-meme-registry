# Реестр мемов

Тема №25: **Реестр мемов**. База данных хранит мемы, их авторов и шаблоны, а также теги, репосты и реакции. Эти данные нужны для каталогизации мемов и анализа их распространения.

| Пункт | Описание |
| --- | --- |
| Главная таблица | `memes` — мемы |
| Связь N:M | Мемы и теги через `meme_tags` |
| Бизнес-правило | Индекс вирусности мема автоматически пересчитывается на основе репостов и реакций. Реализация запланирована на лабораторную №3. |
| СУБД | PostgreSQL 17 в Docker |

## Состав базы данных

- `authors` — авторы мемов.
- `templates` — шаблоны мемов.
- `memes` — мемы, их описания и ссылки на изображения.
- `tags` — теги для классификации мемов.
- `meme_tags` — связующая таблица мемов и тегов.
- `reposts` — репосты мемов на различных платформах.
- `reactions` — реакции на мемы.

В текущей версии репосты и реакции не привязаны к отдельным зарегистрированным пользователям.

## Как запустить

В PowerShell из папки проекта:

```powershell
Copy-Item .env.example .env  # если .env ещё не создан
docker compose up -d
```

При первом запуске скрипты из папки `db/` выполняются автоматически.

Проверка лабораторной №1:

```powershell
dbcheck --lab 1
dbcheck --lab 1 --stars
dbcheck --lab 1 --fresh
```

Подключение к базе:

```powershell
docker compose exec db psql -U postgres -d app
```

Сценарий лабораторной можно запустить внутри `psql`:

```sql
\i /demo/lab1.sql
```

Если локальный порт 5432 занят другой программой, в `.env` можно указать свободный порт, например `DB_PORT=5433`.

**Внимание:** команда `docker compose down -v` удаляет Docker-том вместе со всеми данными PostgreSQL. Используйте её только тогда, когда готовы удалить данные и создать базу заново.

## ER-диаграмма

```mermaid
erDiagram
    authors ||--o{ memes : creates
    templates ||--o{ memes : uses
    memes ||--o{ reposts : has
    memes ||--o{ reactions : receives
    memes ||--o{ meme_tags : classified_by
    tags ||--o{ meme_tags : includes

    authors {
        int id PK
        text display_name
        text username UK
        text bio
        timestamptz created_at
    }

    templates {
        int id PK
        text name UK
        text description
        timestamptz created_at
    }

    memes {
        int id PK
        text title
        text description
        text media_url
        int author_id FK
        int template_id FK
        int viral_index
        timestamptz created_at
    }

    tags {
        int id PK
        text name UK
        text description
    }

    meme_tags {
        int meme_id PK, FK
        int tag_id PK, FK
    }

    reposts {
        int id PK
        int meme_id FK
        text platform
        timestamptz reposted_at
    }

    reactions {
        int id PK
        int meme_id FK
        text reaction_type
        timestamptz created_at
    }
```

Таблица `meme_tags` реализует связь N:M: один мем может иметь несколько тегов, а один тег может относиться к нескольким мемам. Составной первичный ключ `(meme_id, tag_id)` не допускает повторения одной пары.

## Ограничения целостности

| Ограничение | Таблица и колонки | Назначение |
| --- | --- | --- |
| `PRIMARY KEY` | Все таблицы | Уникальная идентификация строк |
| `FOREIGN KEY` | Все колонки со ссылками | Защита от ссылок на несуществующие записи |
| `UNIQUE` | `authors.username` | Уникальные имена пользователей |
| `UNIQUE` | `templates.name`, `tags.name` | Уникальные названия шаблонов и тегов |
| `CHECK` | `memes.viral_index >= 0` | Индекс вирусности не может быть отрицательным |
| `CHECK` | `memes.title` | Название не может быть пустым или состоять только из пробелов |
| `CHECK` | `reposts.platform`, `reactions.reaction_type` | Разрешены только заданные значения |
| `NOT NULL` | Обязательные поля таблиц | Запрет отсутствующих обязательных значений |

## Нормализация до 3НФ

Если бы все данные хранились в одной таблице, пришлось бы повторять имя автора, его никнейм и название шаблона для каждого мема. При нескольких тегах, репостах и реакциях одного мема повторялись бы и сведения о самом меме.

Это создавало бы избыточность: изменение никнейма автора потребовало бы обновления нескольких строк, а при неполном обновлении данные могли бы противоречить друг другу.

Поэтому данные разделены на отдельные таблицы:

1. **Первая нормальная форма (1НФ).** В каждой ячейке хранится одно значение. Теги не записываются списком в одной колонке, а связываются с мемами через `meme_tags`. Репосты и реакции также хранятся отдельными строками.
2. **Вторая нормальная форма (2НФ).** В `meme_tags` используется составной ключ `(meme_id, tag_id)`. В таблице нет дополнительных неключевых полей, зависящих только от части этого ключа. В остальных таблицах используются отдельные первичные ключи `id`.
3. **Третья нормальная форма (3НФ).** Данные автора хранятся в `authors`, шаблона — в `templates`, тега — в `tags`. Таблица `memes` содержит ссылки на автора и шаблон, а не копии их названий и описаний. Таким образом, сведения об отдельных сущностях не дублируются в других таблицах.

## Поведение при удалении (ON DELETE)

Для внешних ключей выбрано следующее поведение:

| Связь | Действие | Причина |
| --- | --- | --- |
| `memes.author_id → authors.id` | `RESTRICT` | Нельзя удалить автора, пока существуют его мемы: сохраняется информация об авторстве. |
| `memes.template_id → templates.id` | `RESTRICT` | Нельзя удалить шаблон, пока на него ссылаются мемы. |
| `meme_tags.meme_id → memes.id` | `CASCADE` | При удалении мема удаляются его связи с тегами. |
| `meme_tags.tag_id → tags.id` | `CASCADE` | При удалении тега удаляются связи с мемами, но сами мемы остаются. |
| `reposts.meme_id → memes.id` | `CASCADE` | Репост без исходного мема не имеет смысла. |
| `reactions.meme_id → memes.id` | `CASCADE` | Реакции на удалённый мем удаляются вместе с ним. |

## Типы данных

- `integer` — идентификаторы и индекс вирусности.
- `text` — названия, описания, ссылки и типы событий.
- `timestamptz` — даты и время создания записей, репостов и реакций.
- `CHECK` со списком значений используется для ограничения платформ репостов и типов реакций.
